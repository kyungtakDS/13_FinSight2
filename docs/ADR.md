# Architecture Decision Records

## 철학

가장 위험한 부분을 가장 먼저 깨본다. **모르는 것만 LLM에 묻고, 답을 캐싱해서 두 번 묻지 않는다.**
개인정보는 필요한 최소한만 다루고, 서버 밖으로는 내보내지 않는다. 요청되지 않은 유연성을 만들지 않는다.
영리한 장치가 그것을 수습하는 장치를 여럿 낳으면, 영리한 쪽을 버리고 평범한 쪽을 택한다.

---

## 제품

### ADR-001: 분류를 규칙과 LLM의 하이브리드로 구성
**결정**: 가맹점명을 전역 `merchant_dictionary`에서 먼저 조회하고, 미매칭 건만 모아 Claude에 1회 배치 호출한다. 결과는 다시 사전에 누적한다.
**이유**: 거래 대부분은 이미 답이 정해진 가맹점(편의점·카페·통신사)이라 LLM이 필요 없다. 전건 호출 시 분석 1회 원가가 약 280원이지만, 하이브리드는 20~40원이다. 더 중요한 것은 사전이 사용자 전체에 걸쳐 누적된다는 점이다 — 사용자가 늘수록 히트율이 오르고 원가는 내려간다.
**트레이드오프**: 사전 관리 로직(적재·갱신·충돌 처리)이 추가된다. 사전이 비어 있는 초기에는 전건 LLM과 원가가 비슷하다. 전역 자산이므로 오염이 전 사용자에게 전파된다 (→ 미해결).

### ADR-002: CSV 컬럼 매핑을 LLM + 지문 캐싱으로 처리
**결정**: 업로드된 파일 상위 20행을 Claude에 보내 헤더 위치와 컬럼 역할(날짜/가맹점/금액)을 판정하고, 그 매핑을 헤더 지문 해시에 묶어 저장한다.
**이유**: 한국 카드사 명세서에는 표준이 없다 — 인코딩이 cp949인 경우가 흔하고, 상단에 메타 블록이 3~7행 깔리며, 컬럼명이 `이용일자`/`거래일자`/`승인일자`처럼 제각각이다. 카드사별 파서를 하드코딩하면 미지원 카드사를 문앞에서 돌려보내야 하고, 카드사가 양식을 바꾸면 조용히 깨진다. LLM 매핑은 카드사 추가에 코드 변경이 필요 없고 양식 변경에 자가 복구된다.
**트레이드오프**: 처음 보는 양식에 1회 LLM 비용(약 10원)과 수 초 지연이 붙는다. 판정이 틀릴 가능성이 있어 신뢰도가 낮을 때의 폴백(수동 매핑 UI)이 언젠가 필요하다.

### ADR-003: LLM에 개인식별정보를 전송하지 않음
**결정**: Anthropic API로 나가는 데이터를 ① CSV 상위 20행 ② 가맹점 상호명 문자열 배열로 한정한다. 금액·날짜·카드번호·사용자 식별자는 전송하지 않는다.
**이유**: 업종 추론에 금액과 날짜는 필요 없다. ADR-001의 사전 구조를 택한 결과, 상호명만 보내도 분류가 성립한다. "누가 언제 얼마를 썼는지는 서버 밖으로 나가지 않는다"는 문장을 약관에 그대로 쓸 수 있다.
**트레이드오프**: 금액 맥락을 활용한 판정(예: 같은 가맹점이라도 고액이면 접대비)을 포기한다. 필요해지면 서버 측 규칙으로 보완한다.
**대체**: 이 결정은 "CSV 전문을 마스킹 후 전송하되 가맹점명과 금액은 그대로 보낸다"는 이전 결정을 폐기한다.

### ADR-004: 산술은 서버가 계산한다
**결정**: 모델 출력은 *거래별 계정과목 · 경비 판정 · 근거 한 줄*까지다. 합계·구성비·추이·**절세 추정액**은 서버 TypeScript가 원본 금액으로 계산한다.
**이유**: 산술을 모델에 맡기면 틀려도 그럴듯해서 검출되지 않는다. 세무 자료에서 합계 오류는 사용자에게 실제 리스크를 넘긴다. ADR-003으로 금액을 아예 보내지 않으므로 모델은 산술을 할 수단도 없다 — 두 결정이 서로를 강화한다.
**트레이드오프**: 집계 코드를 직접 짜야 하고, 모델 출력 배열과 입력 상호명 배열의 인덱스 정합성을 검사해야 한다.

### ADR-005: 원본 파일을 보관하되 90일 후 자동 삭제
**결정**: 업로드 원본을 Storage private 버킷에 암호화 저장하고, 90일 후 **Supabase `pg_cron` 잡**으로 삭제한다. 계정 삭제 시에는 즉시 전량 파기한다. 만료되는 것은 **원본 파일뿐**이며 `transactions`와 리포트는 남는다.
**이유**: 재분석과 분쟁 대응에 원본이 필요하다. 다만 무기한 보관은 정책이 아니라 정책의 부재이며, 시간이 갈수록 보관량과 사고 시 피해 규모가 단조 증가한다. 재분석 수요는 사실상 업로드 직후에 몰려 있어 90일이면 실질 효용을 다 가져간다. 집행 주체를 `pg_cron`으로 못박는 이유는 **Vercel 쪽에 크론이 없고**, 앱 요청에 얹는 lazy expiry는 돌아오지 않는 사용자의 데이터를 영원히 남겨 정책을 무의미하게 만들기 때문이다. 이미 쓰는 Postgres 안에서 끝나 새 인프라가 늘지 않는다.
**트레이드오프**: 개인신용정보를 보관하는 순간 암호화·파기 절차·처리방침 고지·유출 시 신고 의무가 따라붙는다. 90일이 지나면 재시도가 불가능해지므로 UI가 그 사실을 말해야 한다. *구체적 법적 요건은 전문가 검토 필요.*

### ADR-006: 가입을 업로드 앞에 배치
**결정**: 랜딩 → 소셜 가입 → 업로드 → 맛보기 → 결제 순서로 간다. 익명 업로드를 허용하지 않으며, 비로그인 샘플 화면(`/demo`)도 두지 않는다.
**이유**: ADR-005에서 원본을 보관하기로 한 이상, 익명 업로드는 소유자 없는 개인신용정보를 만든다. 그러면 "이 파일 누구 겁니까"에 답할 수 없고 탈퇴 시 삭제도 못 한다. 가입을 앞에 두면 RLS·90일 만료·탈퇴 삭제가 전부 하나의 경로로 처리된다. 또한 ADR-007로 맛보기가 **사용자 자신의 숫자**로 이뤄지므로 남의 샘플을 보여주는 화면의 역할이 사라진다.
**트레이드오프**: 가입 단계에서 이탈이 발생한다. 다만 카드사 CSV 다운로드를 감수한 사용자가 소셜 로그인 원클릭에서 돌아설 가능성은 낮다고 판단했다.

### ADR-007: 무료는 결과 맛보기, 유료는 쓸 수 있는 형태 — 횟수를 세지 않는다
**결정**: 무료로 절세 추정액과 상위 3개 인사이트까지 보여주고, **전체 분류 내역과 세무사 전달용 다운로드**를 유료로 막는다. **분석 횟수 제한을 두지 않는다.** 시계열 대시보드는 MVP 유료 기능에 넣지 않는다 — 유료의 약속은 "세무사에게 넘길 정리본"이고 그것은 내역과 다운로드로 완성된다.
**이유**: ADR-001 덕분에 원가가 낮아 무료 분석을 감당할 수 있다. 사용자가 "내 돈 47만원"이라는 자기 숫자를 본 뒤에 결제하게 되므로, 랜딩 페이지가 혼자 설득을 다 짊어질 필요가 없다. 다운로드를 막았기 때문에 무료로 일을 끝낼 수는 없다. 횟수제는 이 전환 논리를 정면으로 깬다 — 자기 숫자를 보기도 전에 문을 닫기 때문이다.
**트레이드오프**: 전면 유료(트라이얼) 대비 수익 검증이 느리고, 결제하지 않는 사용자의 분석 비용을 부담한다. 무제한 무료가 열려 있어 남용 방어 장치가 없다 (→ 미해결).
**대체**: 이 결정은 "Free 월 3회 / Pro 월 20회"의 횟수제 과금을 폐기한다.

### ADR-008: 구독 종료는 화면을 잠글 뿐 데이터를 지우지 않는다
**결정**: 해지·결제 실패·만료 시 `profiles.plan`을 `free`로 되돌려 유료 화면(전체 내역·다운로드)을 다시 잠근다. `uploads`·`transactions`·리포트는 손대지 않는다. 무료 화면은 과거 분석 전부에 대해 계속 열리고, 이미 다운로드한 파일은 회수하지 않는다.
**이유**: ADR-007의 게이트는 **화면에 걸리는 것이지 데이터에 걸리는 것이 아니다.** 구독 종료를 데이터 파기로 처리하면 재구독 사용자에게 재분석을 강요해 우리 원가를 태우고, 세무 자료를 잃은 사용자에게 신뢰를 잃는다. 데이터를 지우는 주체는 사용자의 삭제 요청·계정 삭제·90일 만료(ADR-005)뿐이라는 규칙이 하나로 유지된다.
**트레이드오프**: 결제하지 않는 사용자의 데이터를 계속 보관하므로 저장 비용과 유출 시 피해 범위가 유지된다. 90일 만료가 이 증가를 상한한다.

### ADR-009: 인증은 Google 단독
**결정**: Supabase Auth의 Google provider만 사용한다. 이메일/비밀번호·매직링크를 만들지 않는다.
**이유**: 타깃이 일반 소비자가 아니라 사업자라 업무용 Google 계정 보유율이 높다. provider를 하나로 고정하면 로그인 분기 코드와 계정 병합 처리, 비밀번호 재설정·이메일 인증 흐름이 통째로 사라진다.
**트레이드오프**: 한국 일반 사용자 침투율이 가장 높은 카카오를 포기한다. 카카오는 비즈앱 전환·검수 절차가 있어 MVP 속도를 깎으므로, 사용자 요구가 확인되면 추가한다.

### ADR-010: MVP는 CSV only
**결정**: XLSX·PDF는 파싱하지 않고 명확한 거부 문구 + 변환 안내를 준다.
**이유**: 한국 카드사가 XLSX를 주는지는 아직 모르고, 파서를 하나 더 만드는 비용이 크다.
**트레이드오프**: 최대 마찰 지점을 의도적으로 남긴다. 거부 문구가 다음 행동(엑셀 → CSV 저장)을 알려주는지가 검토 기준이 된다. 사용자 피드백을 보고 재판단.

### ADR-011: '경비 후보 정리 도구'로 포지셔닝
**결정**: 리포트를 단정적 지시가 아닌 후보 제시로 쓰고, 화면·PDF·약관에 세무 자문이 아님을 명시한다.
**이유**: 세무대리는 세무사의 업무 영역이다. "경비 처리하세요"라고 단정하면 무자격 세무자문으로 해석될 여지가 생기고 오판 시 책임도 우리에게 온다. 한편 PRD의 산출물이 이미 "세무사에게 전달할 정리본"이므로, 판단 주체가 아니라 자료 정리 도구라는 포지션이 마케팅과 모순 없이 성립한다.
**트레이드오프**: 단정적 조언 대비 임팩트가 약하다. *구체적 문구는 법률 전문가 검토 필요.*

### ADR-012: 코어 루프를 먼저 만들고 랜딩을 나중에
**결정**: 프로젝트 초기화 → CSV 파싱 → 분류 엔진 → 리포트·대시보드 → 랜딩 → 결제 순으로 구현한다.
**이유**: 랜딩의 설득력은 실제 리포트 화면 스크린샷에서 나오는데, 그 화면이 없는 상태에서 랜딩을 만들면 목업을 상상으로 그리고 나중에 다시 만들게 된다. 또한 이 제품에서 가장 위험한 부분은 카드사 CSV 파싱이므로, 그것을 가장 먼저 깨봐야 제품이 성립하는지를 가장 빨리 알 수 있다. ADR-007로 랜딩의 설득 부담이 이미 가벼워진 것도 근거다.
**트레이드오프**: 수요 검증(대기자 명단·사전 결제)이 뒤로 밀린다. 코어를 다 만들었는데 아무도 원하지 않을 위험을 감수한다.

## 데이터 정합성

### ADR-013: 분류 실패는 '애매'로 흡수하고 분석을 실패시키지 않는다
**결정**: 분류 실패를 두 층으로 나눈다. **파이프라인 실패**(파싱·매핑·LLM 거부·응답 절단)만 `uploads.status = 'failed'`가 되고, **개별 거래 판정 불확실**은 `transactions.verdict = 'uncertain'`으로 흡수하며 분석은 `completed`다. `uncertain`은 절세 추정액에서 제외하고, 건수를 리포트에 표시한다.
**이유**: 거래 하나를 판정하지 못했다고 300건짜리 분석을 통째로 버리면 사용자는 아무것도 얻지 못한다. 분류를 2값이 아니라 `경비/개인/애매` 3값으로 둔 것이 이 처리를 가능하게 한다. 추정액에서 제외하는 이유는 ADR-011과 같다 — 세무에서 과대 추정은 사용자에게 리스크를 넘기는 행위이므로 추정액은 항상 하한이어야 한다.
**트레이드오프**: `uncertain`이 많으면 리포트의 실효 가치가 떨어지는데, 상태값만으로는 그 저하가 드러나지 않는다. MVP는 건수를 그대로 보여주는 것으로만 메운다 — "비율이 30%를 넘으면 매핑 오판정을 의심한다" 같은 임계치는 실측 없이 숫자를 정하는 일이라 미룬다.

### ADR-014: 리포트는 업로드 1건 단위이고, 중복은 파일 단위로만 막는다
**결정**: 리포트의 단위를 업로드 1건으로 고정한다. 여러 업로드를 가로지르는 합산·시계열을 MVP에서 만들지 않는다. 중복 방지는 `uploads(user_id, file_hash)` 유니크 인덱스 하나 — 같은 파일의 재업로드를 접수 단계에서 거절한다. **거래 지문 기반 교차 파일 중복 판정은 만들지 않는다.** 취소 행은 **상태값의 의미에 따라 나눈다 — 승인이 취소되어 청구되지 않은 건(`void`)은 정규화에서 제외하고, 이미 매입된 거래를 되돌리는 건(`reversal`)만 음수로 상계한다.** 상태 문자열은 카드사마다 다르므로 코드에 두지 않고, 모델이 상태 컬럼의 고유 값만 보고 양식별로 판정해 매핑 캐시(`csv_format_mappings.column_map`)에 함께 저장한다. 상태 컬럼이 없거나 사전에 없는 값은 전부 `normal`이다.
**이유**: 세무 자료에서 과대계상은 누락보다 위험하다. 그런데 **중복 계상은 합산할 때만 생긴다** — 우리가 합산하지 않으면 우리가 중복을 만들지 않는다. 지문 컬럼·인덱스·`is_duplicate` 플래그·"중복 제외 n건" UI는 아직 존재하지 않는 문제를 위한 장치다. 반대로 파일 해시 차단은 인덱스 한 줄로 가장 흔한 실수(같은 파일 두 번)를 무손실로 막는다. 취소를 두 갈래로 나눈 이유는 실측이다 — 국민카드 309행에서 `승인취소` 16건은 **같은 파일에 대응하는 매입 행이 하나도 없고**(결제예정일도 비어 있다) `취소전표매입` 3건은 **3건 모두 가맹점·금액이 일치하는 선행 매입 행이 있다.** 청구된 적 없는 건을 음수로 넣으면 존재하지 않는 환급이 다른 정상 거래에서 깎여 나간다.
**트레이드오프**: 기간이 겹치는 파일 2개를 올린 사용자가 리포트 2개를 손으로 더하면 중복이 된다 — 화면이 "이 리포트는 파일 1개 기준"임을 분명히 말해야 한다. 다중 파일 합산을 도입하는 순간 지문 판정이 함께 들어와야 하며, 그때는 같은 날 같은 가맹점 같은 금액의 진짜 별개 거래(커피 2잔)를 지우지 않도록 **집계 제외 표시**로 설계해야 한다. 취소 판정을 모델에 맡기면 양식마다 LLM 호출이 한 번 늘고, 상태 컬럼이 오매핑되면 그 값들이 전역 캐시로 들어간다 — 고유 값 20개 상한으로 자유 텍스트 컬럼을 걸러 막는다. 제외된 `void` 행은 거래 내역과 세무사 파일에서 사라지므로, 명세서 건수와 리포트 건수의 차이를 인사이트가 건수로 밝힌다.
**개정**: 이 결정은 "취소·부분취소 행은 음수로 정규화해 상계한다"는 이전 문구를 폐기한다. 그 문구의 취지(취소가 합계를 부풀리면 안 된다)는 그대로 승계하되, 상계할 원거래가 없는 취소까지 음수로 만들던 부분을 바로잡는다.

### ADR-015: 정규화된 거래 행을 DB에 저장한다
**결정**: `transactions` 테이블에 정규화된 거래와 분류 결과를 행 단위로 저장한다. 카드번호·승인번호는 정규화 단계에서 제거하며 **컬럼 자체를 두지 않는다**.
**이유**: 유료 기능이 전체 분류 내역과 세무사 전달 파일이므로 행 단위 조회가 필수다. 또한 ADR-005로 원본이 90일 후 사라지는데 리포트는 남아야 하므로, 정규화 행이 DB에 없으면 91일째에 리포트를 재구성할 수 없다.
**트레이드오프**: 보관하는 개인신용정보의 양이 늘어난다. 카드번호·승인번호를 스키마에서 배제해 민감도를 낮췄지만, 거래 내역 자체가 민감정보라는 사실은 남는다.
**대체**: 이 결정은 "거래 원문 행을 DB에 저장하지 말고 집계 요약만 저장한다"는 이전 규칙을 폐기한다. 그 규칙의 취지(불필요한 민감 필드를 남기지 않는다)는 카드번호·승인번호 배제로 승계한다.

## 기술·운영

### ADR-016: Supabase 단일 백엔드
**결정**: Auth · Postgres · Storage를 모두 Supabase로.
**이유**: 인증·DB·파일 저장이 한 SDK와 한 권한 모델(RLS) 안에 들어온다.
**트레이드오프**: 벤더 종속. RLS를 우회하는 service role 경로가 생겨 규율이 필요하다 (ADR-018로 완화). 전역 사전 두 테이블은 RLS 예외이므로 사용자 식별자를 넣지 않는다는 전제를 코드 리뷰에서 지켜야 한다.

### ADR-017: 분석은 비동기 잡 — `after()` + `maxDuration`
**결정**: 접수 라우트가 202를 반환하고 `after()`가 같은 인스턴스에서 처리를 잇는다. 별도 워커·큐 인프라를 두지 않는다.
**이유**: 전역 사전이 채워지면 대부분의 분석은 LLM 0회로 수 초에 끝나지만, 사전이 빈 초기와 처음 보는 카드사 양식에서는 60–180초가 걸린다. **최악 시간이 요청 수명을 넘는 날이 하루라도 있으면 동기 설계는 무너진다.** 큐를 도입하면 의존성과 운영 대상이 늘어난다.
**트레이드오프**: 처리는 여전히 함수 수명 안이다 — 비동기화가 해결하는 것은 **브라우저와의 결합**이지 서버 실행 시간이 아니다. `after()`가 죽으면 행이 `processing`에 남으므로 조회 시점 회수가 필요하다.

### ADR-018: mock-first — 키 없이 전체 검증이 통과해야 한다
**결정**: 외부 호출을 `services/`·`lib/supabase/` 뒤로 격리하고 테스트는 SDK를 mock한다. 환경변수 검증은 lazy.
**이유**: Stop 훅이 매 세션 종료마다 `lint && build && test`를 돌린다. 테스트가 키를 요구하면 **모든 step이 연쇄 실패**한다. 모듈 최상단에서 `process.env`를 읽고 throw하면 `next build`의 프리렌더가 깨진다.
**트레이드오프**: mock이 실제 SDK와 어긋날 수 있다 → 검토 지점의 수동 E2E로 메운다.

### ADR-019: 게이트는 서버에서 판정하고 응답을 잘라서 보낸다
**결정**: `lib/gate.ts`가 `profiles.plan`으로 열람 범위를 정하고, 라우트·서버 컴포넌트가 **잠긴 데이터를 직렬화하지 않는다**. 클라이언트가 보낸 구독 상태를 신뢰하지 않는다. 다운로드 라우트는 파일을 생성하기 전에 plan을 확인한다.
**이유**: 잠긴 데이터를 보내고 CSS·조건부 렌더로 가리면 게이트가 아니라 장식이다. DevTools 한 번이면 유료 기능 전체가 열린다. ADR-007의 과금 모델 전체가 이 한 줄에 얹혀 있다.
**트레이드오프**: 무료/유료 응답 형태가 달라져 컴포넌트가 부분 데이터를 다룰 수 있어야 한다 — 차트·리포트 컴포넌트가 데이터를 props로만 받는 이유다.

### ADR-020: Pro 권한의 source of truth는 서명 검증된 웹훅을 반영한 DB 상태
**결정**: success URL·checkout ID·클라이언트 응답은 권한 근거가 아니다. `profiles.plan`은 검증된 웹훅 transaction 안에서만 바뀐다.
**이유**: 리다이렉트 파라미터로 권한을 열면 누구나 Pro가 된다.
**트레이드오프**: 웹훅 지연 동안 "결제했는데 아직 Free"인 구간이 생긴다 → checkout이 `/dashboard?checkout=1`로 돌아오고, 아직 Free면 "결제 확인 중" 안내를 띄운다. **전용 성공 페이지와 상태 폴링 라우트는 두지 않는다** — 웹훅은 보통 수 초 안에 도착하고, 늦으면 새로고침이 답이다. 쿼리 파라미터가 여는 것은 안내 문구지 기능이 아니므로 이 결정의 보안 성질은 그대로다.

### ADR-021: 웹훅 멱등 기록과 plan 반영은 한 transaction — 구독 테이블은 두지 않는다
**결정**: `webhook_events` INSERT와 `profiles` 갱신(`plan` · `polar_subscription_id` · `source_modified_at`)을 하나의 transaction으로 묶는다. 성능을 이유로 분리하지 않는다. **별도 `subscriptions` 테이블을 만들지 않는다.**
**이유**: 분리하면 크래시 시 이벤트가 *처리됨*으로 기록된 채 반영되지 않고, Polar의 재전송마저 멱등 검사에 걸려 버려진다 → 결제는 성공했는데 영원히 Free. 구독 테이블을 두지 않는 이유는 앱이 묻는 질문이 **"이 사용자가 Pro인가" 하나뿐**이기 때문이다 — 결제수단·영수증·다음 청구일은 ADR-007에서 Polar Customer Portal에 위임했으므로 우리가 미러링할 화면이 없다. 순서 역전 방어에 실제로 필요한 두 필드만 `profiles`에 둔다.
**트레이드오프**: 나중에 청구 이력을 우리 화면에서 보여주려면 테이블을 다시 만들어야 한다. 그때는 Polar API 조회로 먼저 해보고, 그래도 부족하면 만든다.

### ADR-022: 모델은 Claude Opus 5
**결정**: `claude-opus-5`를 `effort: medium`으로 사용한다.
**이유**: 처음 보는 가맹점 상호에서 업종을 추론하고 낯선 CSV 헤더 구조를 판정하는 일은 정확도가 곧 제품 품질이다. ADR-001의 캐시 구조 덕분에 호출 빈도 자체가 낮아, 상위 모델을 써도 총액 영향이 작다.
**트레이드오프**: Sonnet 5 대비 토큰 단가가 약 1.7배다. 캐시 히트율이 기대보다 낮게 나오면 재검토한다.

## MVP에서 미룬 것

폐기가 아니라 **순서**다. 아래는 전부 "아직 존재하지 않는 문제를 위한 장치"라서 뺐고, 각각 돌아올 조건이 붙어 있다.

| 미룬 것 | 뺀 이유 | 돌아오는 조건 |
|---|---|---|
| 시계열 대시보드 | 유료의 약속은 "세무사에게 넘길 정리본" — 내역+다운로드로 완성된다 | 다중 파일 합산과 함께 |
| 다중 파일 합산 | 리포트를 업로드 1건 단위로 두면 중복 문제 자체가 없다 | 사용자가 파일을 나눠 올린다는 실측 |
| 거래 지문 교차 중복 판정 (`fingerprint`·`is_duplicate`) | 합산하지 않으면 중복 계상이 생기지 않는다 | 다중 파일 합산 도입 시 **동시에** |
| `subscriptions` 테이블 | 앱이 묻는 건 "Pro인가" 하나. 나머지는 Polar Portal이 보여준다 | 청구 이력을 우리 화면에 넣을 때 (Polar API 조회 먼저 시도) |
| `/billing/success` + `/api/billing/status` 폴링 | 웹훅은 보통 수 초. 늦으면 새로고침이 답이다 | 웹훅 지연이 실제로 문제가 될 때 |
| `uncertain` 비율 임계치 자동 진단 | 실측 없이 30% 같은 숫자를 정하는 일 | 오분류 데이터가 쌓인 뒤 |
| 비정규화 카운트 컬럼 (`uncertain_count`·`duplicate_count`) | MVP 규모에서 `transactions` 집계로 충분 | 목록 조회가 느려질 때 |
| `merchant_dictionary.hit_count` | 아무 코드도 읽지 않는다 | 사전 히트율을 실제로 계측할 때 |
| 클라이언트 에러 어휘 10 → 7 | 사용자가 취할 행동이 같으면 같은 코드다. 진단 구분은 로그에 남긴다 | — |

## 미해결

- **무료 남용 방어**: 횟수제(폐기)를 대신할 장치가 없다. ADR-001의 저원가 전제가 실측으로 깨지면 필요해진다. Google 계정 재생성으로 우회 가능하다는 점도 함께 고려해야 한다
- **Pro 가격**: ₩9,900은 횟수제 시절 가설이다. 게이트 모델에서 재검증 필요
- **전역 사전 오염**: 잘못된 항목 1건이 전 사용자에게 전파된다. 신뢰도 점수·출처 추적·롤백 설계가 없다. 현재 방어는 "고정 목록 검증을 통과한 항목만 적재" 하나뿐이다
- **컬럼 매핑 오판정 폴백**: 수동 매핑 UI가 MVP 제외라, 매핑이 틀리면 사용자가 할 수 있는 일이 재시도뿐이다
