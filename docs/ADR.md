# Architecture Decision Records

## 철학
가장 위험한 부분을 가장 먼저 깨본다. 모르는 것만 LLM에 묻고, 답을 캐싱해서 두 번 묻지 않는다. 개인정보는 필요한 최소한만 다루고, 서버 밖으로는 내보내지 않는다. 요청되지 않은 유연성을 만들지 않는다.

---

### ADR-001: 분류를 규칙과 LLM의 하이브리드로 구성
**결정**: 가맹점명을 전역 `merchant_dictionary`에서 먼저 조회하고, 미매칭 건만 모아 Claude에 1회 배치 호출한다. 결과는 다시 사전에 누적한다.
**이유**: 거래 대부분은 이미 답이 정해진 가맹점(편의점·카페·통신사)이라 LLM이 필요 없다. 전건 호출 시 분석 1회 원가가 약 280원이지만, 하이브리드는 20~40원이다. 더 중요한 것은 사전이 사용자 전체에 걸쳐 누적된다는 점이다 — 사용자가 늘수록 히트율이 오르고 원가는 내려간다.
**트레이드오프**: 사전 관리 로직(적재·갱신·충돌 처리)이 추가된다. 사전이 비어 있는 초기에는 전건 LLM과 원가가 비슷하다.

### ADR-002: CSV 컬럼 매핑을 LLM + 지문 캐싱으로 처리
**결정**: 업로드된 파일 상위 20행을 Claude에 보내 헤더 위치와 컬럼 역할(날짜/가맹점/금액)을 판정하고, 그 매핑을 헤더 지문 해시에 묶어 저장한다.
**이유**: 한국 카드사 명세서에는 표준이 없다 — 인코딩이 cp949인 경우가 흔하고, 상단에 메타 블록이 3~7행 깔리며, 컬럼명이 `이용일자`/`거래일자`/`승인일자`처럼 제각각이다. 카드사별 파서를 하드코딩하면 미지원 카드사를 문앞에서 돌려보내야 하고, 카드사가 양식을 바꾸면 조용히 깨진다. LLM 매핑은 카드사 추가에 코드 변경이 필요 없고 양식 변경에 자가 복구된다.
**트레이드오프**: 처음 보는 양식에 1회 LLM 비용(약 10원)과 수 초 지연이 붙는다. 판정이 틀릴 가능성이 있어 신뢰도가 낮을 때의 폴백(수동 매핑 UI)이 언젠가 필요하다.

### ADR-003: LLM에 개인식별정보를 전송하지 않음
**결정**: Anthropic API로 나가는 데이터를 ① CSV 상위 20행 ② 가맹점 상호명 문자열 배열로 한정한다. 금액·날짜·카드번호·사용자 식별자는 전송하지 않는다.
**이유**: 업종 추론에 금액과 날짜는 필요 없다. ADR-001의 사전 구조를 택한 결과, 상호명만 보내도 분류가 성립한다. "누가 언제 얼마를 썼는지는 서버 밖으로 나가지 않는다"는 문장을 약관에 그대로 쓸 수 있다.
**트레이드오프**: 금액 맥락을 활용한 판정(예: 같은 가맹점이라도 고액이면 접대비)을 포기한다. 필요해지면 서버 측 규칙으로 보완한다.

### ADR-004: 원본 파일을 보관하되 90일 후 자동 삭제
**결정**: 업로드 원본을 Storage private 버킷에 암호화 저장하고, 90일 후 배치로 삭제한다. 계정 삭제 시에는 즉시 전량 파기한다.
**이유**: 재분석과 분쟁 대응에 원본이 필요하다. 다만 무기한 보관은 정책이 아니라 정책의 부재이며, 시간이 갈수록 보관량과 사고 시 피해 규모가 단조 증가한다. 재분석 수요는 사실상 업로드 직후에 몰려 있어 90일이면 실질 효용을 다 가져간다.
**트레이드오프**: 개인신용정보를 보관하는 순간 암호화·파기 절차·처리방침 고지·유출 시 신고 의무가 따라붙는다. 무저장(stateless) 대비 컴플라이언스 부담이 크다. *구체적 법적 요건은 전문가 검토 필요.*

### ADR-005: 무료는 결과 맛보기, 유료는 쓸 수 있는 형태
**결정**: 무료로 절세 추정액과 상위 3개 인사이트까지 보여주고, 전체 분류 내역·시계열·다운로드를 유료로 막는다.
**이유**: ADR-001 덕분에 원가가 낮아 무료 분석을 감당할 수 있다. 사용자가 "내 돈 47만원"이라는 자기 숫자를 본 뒤에 결제하게 되므로, 랜딩 페이지가 혼자 설득을 다 짊어질 필요가 없다. 다운로드를 막았기 때문에 무료로 일을 끝낼 수는 없다.
**트레이드오프**: 전면 유료(트라이얼) 대비 수익 검증이 느리고, 결제하지 않는 사용자의 분석 비용을 부담한다.

### ADR-006: 가입을 업로드 앞에 배치
**결정**: 랜딩 → 소셜 가입 → 업로드 → 맛보기 → 결제 순서로 간다. 익명 업로드는 허용하지 않는다.
**이유**: ADR-004에서 원본을 보관하기로 한 이상, 익명 업로드는 소유자 없는 개인신용정보를 만든다. 그러면 "이 파일 누구 겁니까"에 답할 수 없고 탈퇴 시 삭제도 못 한다. 가입을 앞에 두면 RLS·90일 만료·탈퇴 삭제가 전부 하나의 경로로 처리된다.
**트레이드오프**: 가입 단계에서 이탈이 발생한다. 다만 카드사 CSV 다운로드를 감수한 사용자가 소셜 로그인 원클릭에서 돌아설 가능성은 낮다고 판단했다.

### ADR-007: 인증은 Google 단독
**결정**: Supabase Auth의 Google provider만 사용한다.
**이유**: 타깃이 일반 소비자가 아니라 사업자라 업무용 Google 계정 보유율이 높다. provider를 하나로 고정하면 로그인 분기 코드와 계정 병합 처리가 아예 생기지 않는다.
**트레이드오프**: 한국 일반 사용자 침투율이 가장 높은 카카오를 포기한다. 카카오는 비즈앱 전환·검수 절차가 있어 MVP 속도를 깎으므로, 사용자 요구가 확인되면 추가한다.

### ADR-008: '경비 후보 정리 도구'로 포지셔닝
**결정**: 리포트를 단정적 지시가 아닌 후보 제시로 쓰고, 화면·PDF·약관에 세무 자문이 아님을 명시한다.
**이유**: 세무대리는 세무사의 업무 영역이다. "경비 처리하세요"라고 단정하면 무자격 세무자문으로 해석될 여지가 생기고 오판 시 책임도 우리에게 온다. 한편 PRD의 산출물이 이미 "세무사에게 전달할 정리본"이므로, 판단 주체가 아니라 자료 정리 도구라는 포지션이 마케팅과 모순 없이 성립한다.
**트레이드오프**: 단정적 조언 대비 임팩트가 약하다. *구체적 문구는 법률 전문가 검토 필요.*

### ADR-009: 코어 루프를 먼저 만들고 랜딩을 나중에
**결정**: 프로젝트 초기화 → CSV 파싱 → 분류 엔진 → 리포트·대시보드 → 랜딩 → 결제 순으로 구현한다.
**이유**: 랜딩의 설득력은 실제 리포트 화면 스크린샷에서 나오는데, 그 화면이 없는 상태에서 랜딩을 만들면 목업을 상상으로 그리고 나중에 다시 만들게 된다. 또한 이 제품에서 가장 위험한 부분은 카드사 CSV 파싱이므로, 그것을 가장 먼저 깨봐야 제품이 성립하는지를 가장 빨리 알 수 있다. ADR-005로 랜딩의 설득 부담이 이미 가벼워진 것도 근거다.
**트레이드오프**: 수요 검증(대기자 명단·사전 결제)이 뒤로 밀린다. 코어를 다 만들었는데 아무도 원하지 않을 위험을 감수한다.

### ADR-010: 모델은 Claude Opus 5
**결정**: `claude-opus-5`를 사용한다.
**이유**: 처음 보는 가맹점 상호에서 업종을 추론하고 낯선 CSV 헤더 구조를 판정하는 일은 정확도가 곧 제품 품질이다. ADR-001의 캐시 구조 덕분에 호출 빈도 자체가 낮아, 상위 모델을 써도 총액 영향이 작다.
**트레이드오프**: Sonnet 5 대비 토큰 단가가 약 1.7배다. 캐시 히트율이 기대보다 낮게 나오면 재검토한다.
